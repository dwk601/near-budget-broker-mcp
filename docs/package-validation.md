# Package validation and verified compatibility

## Run

```sh
npm ci
npm run test:package && npm run typecheck
```

The package suite cleans and builds `dist` itself before it packs, so the project has no prepack hook and does not need one. To build a tarball for operators, remove `dist`, run `npm run build`, then run `npm pack`. You need Node 24 or later and Docker Compose 2.24.4 or later. The render tests start no containers and need no Docker daemon. Installing npm dependencies may need registry access. The packaging tests use no live faucet, no payments, and no public NEAR RPC.

## What the package suite checks

`test/package/package.test.ts` creates one OS temp directory and a fresh consumer project outside the checkout. It then runs these checks:

1. It removes `dist` so that stale build output cannot ship, runs the build, runs `npm pack --json --pack-destination TEMP`, and installs the tarball in the fresh project with install scripts disabled. It handles both pack manifest formats: the array format from npm 11 and earlier and the package-keyed format from npm 12. The installed bin resolves inside the consumer project, not the worktree.
2. It inspects the real archive and compares its entries. It requires `dist`, the bin, `README.md`, `LICENSE`, the skill, the examples, and the Docker files. Examples, Docker files, and skills must match exact filename allowlists, and generated `dist` files are allowed separately. It rejects tests, `node_modules`, `.env`, state and database files, and private key or token material, including bare `ed25519:` base58 secrets and `private_key` or `secret_key` JSON. Regression cases confirm that it rejects unreviewed `native-key`, `owner.json`, `receivers.json`, and `fixtures.env` files. The package has no postinstall hook.
3. It parses every shipped example JSON file. It validates the npx arguments and version in the MCP examples, checks the policy and grant shapes with exact NEAR conversion, and validates the skill's simple YAML `name` and `description` frontmatter. It replaces only the public key placeholder in the daemon config with a temporary real public key and loads the result through the production config loader, which also converts yoctoNEAR amounts.
4. It runs the installed bin with a missing token and with a nonexistent token file. Both must exit nonzero and write only a clean message to stderr, with no stdout, stack traces, or token text. It also runs real local encrypted owner and custody key creation, the config flag with its environment fallback, a valid offline verification of signed receipts against a checkpoint, and failures on corrupt JSON, schema, and signatures. A missing receipt file must exit 1 with `AUDIT_UNAVAILABLE` in both text and JSON modes. An invalid audit key with parseable inputs must exit 1 with `valid:false` on stdout and empty stderr.
5. It runs 32 owner admin command forms, including optional positional arguments and flags, against a local stub that records requests. The CLI unlocks a real encrypted owner key and sends real signed HTTP requests. The stub validates the strict admin schemas, but it is not a live broker and does not test owner authentication security. Inputs use UUIDs, not generic labels. The tests check amount conversion, `--force` behavior, sequence exports, protected token files, and the path and credentialId output in both plain and JSON form. Refusal cases check the documented exit codes 0, 1, 2, and 3, including exit 2 for a stale policy revision and exit 3 for authorization.
6. It checks the help variants without credentials or network. `docs/cli-help.txt` is captured from the real CLI help and compared byte for byte with the installed help. Root and owner help print to stdout. `mcp --help` and `help mcp` print to stderr and leave stdout empty. All exit 0.
7. It times 30 separate runs of the installed `--help`, prints the nearest-rank p95, and requires it to be 1000 ms or less, with real help text, exit 0, and no stderr. Fast usage errors do not count as samples. The suite prints the timing directly to stdout so it stays visible even when Vitest hides console output from passing tests.
8. It removes the consumer project, the tarball, and temporary secrets during suite cleanup, even after an assertion or setup failure. Only the normal git-ignored `dist` output remains. It writes no fixture, state, or tarball files into the checkout.

The package suite also renders the shipped Compose files with real `docker compose config --quiet` and JSON assertions through `assertComposeConfig`. It renders the base file alone, base plus prebuilt, base plus resources, and all three together. It checks the file-secret paths, `BB_IMAGE`, `BB_DATA_VOLUME`, the loopback ports, that the named volume is the only mount, that the hardening settings remain, that the prebuilt override removes the build section, and the resource limits. It compares the installed build context with the package root using canonical paths, which handles aliases of the current directory. Before the shared helper runs its exact base deployment assertions, the suite normalizes only the validated context and override differences, on a copy of the config. Rendering creates no images, containers, volumes, or networks.

`test/package/lifecycle.test.ts` runs the production broker defaults with a fake chain and clock. A pending approval is still pending at 299999 ms, expires at 300000 ms, and releases both holds. Queued work and stored approved work also expire on the dispatch pass at 300000 ms during a global freeze. They release both holds, and neither unfreezing nor replaying the same key revives them. Expired, rejected, and cancelled requests keep their keys. Denials stored for `RATE_LIMITED` or `MAX_OUTSTANDING` stay denied after backoff and after capacity recovers, while a new authorized request can still be admitted. When queued work meets a standing grant it was never bound to, it returns to pending owner approval without signing, broadcasting, or using that grant. An explicit owner approval then lets the same request execute.

`npm run test:cli` also runs the current CLI and main entry point against a fake chain and RPC. It covers local validation, stale policy revisions, verification of corrupt data, exit codes for authentication and Host or Origin failures, every daemon diagnostic, per-key locks across data directories, and crash recovery. `npm run test:isolation` runs a real Docker build, create, provision, and up with file secrets and a read-only root filesystem, then kills the daemon with SIGKILL and restarts it, all against an isolated fake RPC.

## Compatibility assumptions

- The package is private, and npx installs it from a local tarball. Nothing claims it is published to the registry. A clean build before packing is required, and the suite performs it. There is no prepack hook.
- The tarball allowlist includes the README, examples, skill, Docker files, and `dist`. It leaves out the full docs, `src`, the fixture scripts, the lockfile, and the compiler config on purpose, so the README's links to the full guides point into the source checkout. Build the daemon image and run live fixtures from source, or supply a separately trusted image through `BB_IMAGE` and the prebuilt override.
- Of the fixture files, only `broker-key.json` is encrypted. Use it with the exact binary `master.secret`. `recovery.json` (a full-access key) and `receivers.json` hold plaintext ed25519 private keys with mode 0600, and the whole fixtures directory, including the master, is secret. The base Compose file secrets already accept that binary file through `BB_MASTER_FILE`. No environment or inline secret override remains.
- The absolute `BB_MASTER_FILE` and `BB_CONFIG_FILE` paths are a protected operator exception. Both files live outside the repository, with mode 0600, in 0700 directories. The master must be a regular file, not a symlink, with mode 0600 or 0400, and owned by the daemon uid (mapped uid 1000). Read access alone is not enough. That uid must be able to read the config. A master file that fails these checks causes `BAD_MASTER_SECRET`. The daemon receives `BB_MASTER_SECRET_FILE` and refuses a direct `BB_MASTER_SECRET`. Keep the image and volume variables consistent, run Compose `create` before provisioning, and provision the encrypted envelope over stdin at `/var/lib/budget-broker` as uid 1000.
- `broker.sqlite` and its WAL and SHM sidecars have mode 0600, even under a loose umask, and the daemon refuses symlinks for all of them. The SQLite data lock and the per-custody-key lock files stay on disk, and the kernel releases the locks after a crash. No stale PID or temporary lock deletion step applies to current locks. Separate users, hosts, or volumes do not share locks. One daemon and one trust root per custody key is still mandatory.
