# Security model and explicit limits

## Trusted and untrusted components

Untrusted: mutually hostile agents, their prompts/tool inputs, MCP sessions and request IDs. Trusted: operator signing environment, host/kernel/container runtime, daemon code/dependencies, storage/audit root, and configured RPC's truthful retained final history. This is **testnet-only experimental native NEAR custody**, not production custody, multi-party consensus, or a defense against a malicious host/RPC.

Only the daemon has the encrypted custody key, unlock secret, DB and private audit key. The stdio bridge receives a protected scoped bearer token, URL and MCP bytes, not a wallet key. Agent identity is authenticated on every HTTP/tool operation, including existing sessions; session IDs are not credentials. Request/receipt lookups are ownership-filtered. Tokens are random bearer secrets stored as hashes server-side; stealing one compromises that agent's allowed capabilities until revoked. An agent can spend its entire allowed budget and freeze itself; policy is not intent validation.

The owner CLI signs method/path/body-hash/nonce/time with a separate encrypted Ed25519 owner key. The daemon holds only the public owner key. Owner requests have a 60s time window and durable replay protection. The admin port exposes bounded broker operations, not arbitrary SQL/signing or an owner transfer bypass. Owner policy/approval authority is highly privileged: protect it.

## Isolation is a deployment requirement

**Agents must not have Docker socket/control, root, owner key/passphrase, custody/recovery keys, master material, daemon named-volume or provisioning-environment access.** A same-user shell can often inspect files, environment, processes or Docker: run it under a **separate OS user or properly isolated container/sandbox** without those capabilities. A second terminal, hidden filename, chmod under the same uid, or encrypted-at-rest file beside an available unlock secret is not a boundary. Host administrators/Docker users can inspect an unlocked daemon. Encryption protects locked data, not a compromised process.

No Docker socket or host credential-directory mounts. Named-volume custody/DB, separate **file-backed** Compose secrets, read-only rootfs, uid 1000, no-new-privileges and dropped capabilities reduce accidental exposure but do not defeat host control. `BB_MASTER_FILE`/`BB_CONFIG_FILE` are absolute protected host paths outside the repo (0600 files, 0700 parent directories), readable by mapped container uid 1000, never agents; these two secret-file mounts are the explicit operator exception, not state-directory binds. Binary master bytes stay verbatim in the file. The daemon accepts `BB_MASTER_SECRET_FILE` and refuses direct `BB_MASTER_SECRET` even alongside a file. Raw custody/owner keys never enter the daemon image/build context; only the encrypted envelope crosses stdin. Compose create initializes a fresh volume at /var/lib/budget-broker before provisioning, preserving uid 1000 ownership. Fixture recovery keys are a separate full-access escape hatch protected from agents too.

Agent/admin host publications bind 127.0.0.1, not 0.0.0.0; validate Host/Origin against DNS rebinding. Do not trust forwarded headers or disable authentication for loopback clients. Default browser Origins are denied; bearer tokens are not owner capabilities. An agent container needs an explicit restricted route to the daemon, not a public admin publication.

## Accounting, authorization and audit

Fail closed: missing/expired policies, zero caps, freeze/revocation, stale/unknown balance, invalid monetary values and audit failure deny spending. Native transfer only, fixed signer, explicit persisted nonce/signed bytes, testnet RPC identity check, no arbitrary action or mainnet fallback. Bigint/u128 arithmetic and integer yocto text avoid floating-point money.

Atomic admission combines current authorization, scoped idempotency, reservations and signed decision. Pending approvals reserve principal+gas. Standing approvals bypass only the approval gate, not hard caps. Final authorization shares serialization with freeze/policy/revocation writes before broadcast invocation. Freeze cannot recall offered payments, and ambiguous outcomes retain holds. Actual transaction plus receipt fees belong to the requesting agent, even on failed execution; real fees above reserve still count. Preview/remaining quota never guarantees shared-wallet capacity.

One daemon process, database and volume/trust root per custody key. Lifetime SQLite EXCLUSIVE kernel locks protect dataDir/daemon.lock and a per-custody-public-key database in the stable OS-account-home/.budget-broker-locks directory. This fences the key across data dirs/ports in one OS user/namespace, independent of HOME/TMPDIR; unsafe existing lock permissions are refused. Kernel locks release on SIGKILL/crash, while **lock files must remain and never be unlinked/replaced**. The image places OS-account home/key locks on the same private named volume. However, **independent users/containers/hosts with different volumes are not fenced**; no active-active/distributed leadership. Keep BB_IMAGE/BB_DATA_VOLUME consistent and one trust root per key. An old text O_EXCL lock needs one-time migration only after the old daemon stops; never apply that deletion procedure to current SQLite locks.

Persist before broadcast; reuse exact signed bytes after ambiguity. Missing indexer/transaction visibility, timeouts and InvalidNonce alone do not prove non-execution. Automated replacement can follow either of two independent non-execution proof paths:

- **First-rejection nonce proof:** exactly one offer with definitive first-offer `EXPIRED_BLOCK_HASH` rejection, or `INVALID_NONCE` provenance with the rejected transaction's nonce and a strictly greater rejection-time access-key nonce. A fresh access-key view pinned to the final head must have nonce **>= the attempt nonce**.
- **Expiry proof:** any offer count, with no first-rejection provenance required. The access-key nonce pinned to the final head must be **strictly below the attempt nonce**; final height must be at least anchor height + protocol transaction validity period + **1000 blocks**; signing age must be at least validity period × **1000 ms**; and two definitive `UNKNOWN_TRANSACTION` lookups must be spaced at least **1 s** apart. A consumed nonce vetoes this expiry path even beyond that margin.

Both paths verify the persisted signed bytes, require a recorded last offer at least **60 s** old, retrievable matching anchor history, and a second negative lookup after the final-head-pinned key observation. Both feed the same `proven_not_executed` replacement flow, which rechecks exclusion and current authorization before committing/sending a replacement. They rely on the **trusted RPC's truthful retained final history**; missing/GC'd history fails closed, and a lying/stale RPC is not independently disproved. See [proof and replacement details](architecture.md#b06f-m1l4-separate-nonce-and-generous-expiry-exclusion-rules).

Owner `resolve-attempt` normally requires fresh exclusion. Pending or final execution evidence vetoes even `--force`. For **offered uncertain bytes**, force can retire the lane item as failed but retains principal+fee holds; fresh exclusion can release them. For **never-offered signed bytes**, force instead abandons the request and releases both holds, with no resolution watch. Never-offered means durable broker evidence shows no submission intent or acknowledgment, not merely no visible transaction. Automatic post-resolution watches for offered work stop after **more than 60 h from the later of signing and the last recorded offer**, without freeing uncertain holds. Afterwards use explicit `owner reconcile REQUEST_ID`; unscoped reconcile does not extend automatic watches. Watched late actual outcomes are charged once on both receipt chains and trigger global freeze for review. Uncertainty may retain funds indefinitely; the watch horizon is not proof of non-execution. Never manually erase holds to restore capacity.

Independent per-agent and owner receipt chains use SHA-256 canonical preimages and a distinct audit Ed25519 key. Audit/signature failure rolls back mutations. Signatures prove possession of a trusted key, not truth of a compromised daemon/RPC, full historical availability, or absence of truncation. Independently pin the public audit key and external checkpoints. A local DB/checkpoint cannot detect its own rollback; a retained external pin protects only through its sequence. Newer deleted suffixes remain undetectable without newer pins. Audit key compromise permits forged history; backup/monitor the trust root.

## Not provided

Mainnet, FT, contract calls, arbitrary signing/key management, active-active fencing, guaranteed payment liveness, fee estimates as final accounting, automated release on timeouts, unprivileged defense against host/Docker/root access, or production-grade custody guarantees. Independent RPC/chain auditing, external checkpoint retention, OS isolation and secret lifecycle remain operator duties.
