# Troubleshooting

While diagnosing a problem, never print keys or tokens, never log protocol messages to stdout, never delete accounting holds, never disable authentication, and never publish ports publicly.

| Symptom | What to check and what to do |
| --- | --- |
| Node, sqlite, or import failure | Use Node 24 or later. Rebuild from source and install a fresh tarball. Remove any old global `budget-broker` bin |
| Help appears on stderr and stdout is empty | Expected for `mcp --help` and `help mcp`, which exit 0. Top-level `--help` and `help` print to stdout. The general help is captured in `cli-help.txt` |
| `Budget Broker bridge: invalid URL or protected token file` | Set both `BB_URL` and `BB_TOKEN_FILE`. The URL must be the root or `/mcp`, with no credentials, query, or fragment, and must use HTTP on loopback or HTTPS. The token file must be a regular file owned by the caller, not a symlink, with no group or other permission bits, valid token syntax, and at most 4096 bytes |
| MCP starts but the tools are unavailable | The bridge connects to the daemon only when first needed. Check that the daemon is running, the port and host are exact, the token is not revoked, and the network route works. Bridge stderr carries diagnostics, and stdout carries only protocol |
| `UNAUTHENTICATED` after rotation | Give the agent the new token file securely and reconnect. Reusing an old session does not restore a revoked credential |
| Creating a token or output file fails | Outputs are created new and never overwrite. Pick a new protected path. `token issue` and `token rotate` print the path and the credentialId (an object with `--json`), so do not read the whole of stdout as a filename. The token itself stays only in its file |
| Owner command returns `FORBIDDEN` | Check the owner key's mode and owner, the passphrase, and whether you are on a TTY that hides input or in protected automation. Check the admin URL, Host, and Origin. The clock must be within 60 seconds of the daemon. Do not send a bearer header to the admin port |
| Owner command hangs or fails offline | Most owner commands contact the admin port. Only help, key creation, and `receipts verify` run locally. CLI IDs must be broker-issued UUIDs, not labels. Local argument, policy, and grant validation errors and stale policy revisions exit 2. Authentication and authorization failures, including Host or Origin rejection on writes, exit 3 |
| `NO_POLICY` or a zero budget | Set both the agent policy and the wallet policy. Check the agent ID, revision, and expiry. Zero means zero. Check whether the agent froze itself |
| `INVALID_AMOUNT` | MCP, config, and the wire format use integer yoctoNEAR strings. Policy and grant files for the CLI use human NEAR strings. Never use numbers, exponents, or whitespace. A transfer must be above zero and fit in a u128 |
| `WALLET_CAPACITY` with a positive balance | Storage, locked balance, the safety reserve, and all holds reduce what is spendable. A stale or failed RPC read denies spending. The fixture check confirms a positive balance, not available capacity |
| `GAS_BUDGET_EXCEEDED` | The agent's actual burnt tokens and its fee holds both count, including fees from failed transfers. Actual overages cannot be hidden or refunded |
| `APPROVAL_REQUIRED` or a pending request | Inspect the existing request and ask the owner to approve or reject it. Do not repeat it with new keys. Queued or approved work cannot start using a standing grant it was never bound to. It returns to pending owner approval instead. Hard caps still apply |
| `POLICY_CHANGED` on approval | Reread the request and policy, and review the current digest and revision. Do not approve stale work without review |
| `IDEMPOTENCY_CONFLICT` | The same agent used this key with a different payload. Inspect the original request and reconcile it before sending a genuinely new intent |
| A submitted or unknown request is stuck | Keep the ID, key, and holds. `owner reconcile` polls only existing attempts and watches. Missing history is not proof of anything. Never create a duplicate payment with a new key |
| A resolved request stopped being polled | For offered work, automatic watches after resolution stop once more than 60 hours have passed since signing or the last recorded offer, whichever is later. The clock does not start at resolution, and stopping never releases uncertain holds. Run `owner reconcile REQUEST_ID` after that. An unscoped `reconcile` does not extend the watch. Unavailable or garbage-collected RPC history proves nothing. If reconciliation finds a late execution, the broker charges it once and sets a global freeze for review |
| Queued or approved work expired while frozen | The fixed 300-second deadline from creation also covers queued and approved work before signing. A freeze does not pause it. The next dispatch pass after the deadline expires the request and releases its principal and fees. Unfreezing cannot revive it or free its key, and any new key or request needs owner authorization. Never retry after rejection |
| Forced resolution did not restore budget | For offered bytes with an uncertain outcome, `--force` removes the lane item but keeps the principal and fees until fresh exclusion evidence or the actual execution appears. For signed bytes that were never offered, forcing abandons the request and releases both holds with no watch. Evidence of a pending or executed transfer blocks both. A `failed` state alone does not prove the funds were released |
| Agent unfreeze did not restart failed work | Signed requests that were never offered may have been abandoned permanently. The owner must authorize a genuinely new intent and key. Never revive signed history |
| Global freeze after a standing overrun | The broker still records the executed principal and gas. It revokes the grant and keeps other reservations. Review accounting and receipts before the owner unfreezes. Never erase the executed payment |
| Global freeze after a late execution | Review the signed `lateResolution` receipts on both chains, and the actual principal, gas, and any standing overrun. Reconcile before the owner unfreezes |
| `AUDIT_UNAVAILABLE` from the daemon or MCP | Stop spending. Check the protected volume's free space and integrity and the retained audit root. Restore a consistent backup instead of creating a fresh audit key next to old history. For offline `owner receipts verify`, see the last row of this table |
| `BROKER_UNAVAILABLE` at startup | Read the redacted diagnostic reason, listed in the next section. Do not expose the raw config, environment, or keys |
| A lock file remains after a crash | This is expected. The kernel releases SQLite locks automatically. Keep the files and never unlink or replace them. Same-key locks live in the OS account home, not `HOME` or `TMPDIR`. Only the old text O_EXCL format needs a migration, after the old daemon stops. See the operator guide |
| Fixture faucet outage | Rerun apply with the same external directory. Do not regenerate the account or keys. `--check` never provisions missing state |
| The fixture envelope fails with `init-custody` | The envelope is already encrypted. Use `broker-key.json` with the binary `master.secret` as they are. `init-custody` accepts only raw ed25519 text |
| Compose secret decryption fails | The base file uses file secrets. Set `BB_MASTER_FILE` to the exact binary `master.secret` and `BB_CONFIG_FILE` to the edited config, as absolute paths outside the repository, with 0600 files in a 0700 parent. The master must be a regular file, not a symlink, owned by the mapped daemon uid 1000, with mode 0600 or 0400. That uid must be able to read the config. Do not loosen permissions. You do not need an environment or inline secret override |
| Compose override tag error | The prebuilt `!reset` tag needs Compose 2.24.4 or later. Set `BB_IMAGE` consistently, and validate with `config --quiet` without logging secrets |
| Docker build from the tarball fails | The tarball leaves out `src`, the lockfile, and `tsconfig` on purpose. Build the image from a source checkout or use a trusted prebuilt override |
| An agent in a container cannot reach localhost | The container's localhost is not the host loopback. Set up a restricted route in your deployment. Never publish the admin port publicly |
| Offline receipt verification fails | The export starts at genesis. Pass one retained checkpoint object, not the array, and a public audit key that you pinned separately. A missing or unreadable file or a JSON or schema parsing failure exits 1 with `Budget Broker: AUDIT_UNAVAILABLE` (`{error:{code:"AUDIT_UNAVAILABLE"}}` with `--json`). Here that means a local input problem, not a failure of the daemon's audit volume. If the files parse but the audit key is wrong, the command prints `valid:false` JSON on stdout, writes nothing to stderr, and exits 1, also with `--json`. Check the paths, the file contents, and the public key. Corrupt JSON, schema, signature, or checkpoint data also exits 1. A missing required flag exits 2. Never replace the pin or key just to get `valid:true` |

## Daemon diagnostics

These reasons are not MCP or domain codes. Each one comes with the domain code `BROKER_UNAVAILABLE` and exit code 1. The text form is `Budget Broker: REASON`, and the `--json` form is `{error:{code:"BROKER_UNAVAILABLE",reason:"REASON"}}`. They never include paths, values, stack traces, or environment dumps. The first failing startup check can hide other problems behind it.

| Reason | What to do |
| --- | --- |
| `BAD_CONFIG` | Check that the file exists, that the JSON and config shape are valid, and the paths inside the container. Config must not contain secret values |
| `BAD_MASTER_SECRET` | `BB_MASTER_SECRET_FILE` must be a regular file, not a symlink, with mode 0600 or 0400, owned by the daemon uid. Check that its length is 32 to 4096 bytes and that the bytes match the envelope exactly. Do not trim or re-encode the file |
| `MASTER_SECRET_ENV_REFUSED` | Remove `BB_MASTER_SECRET` completely, even if `BB_MASTER_SECRET_FILE` is also set. The daemon unlocks only from a file |
| `LISTEN_FAILED` | The port or interface is unavailable or already bound. Check the host, the config, and the port publications. Never publish publicly |
| `DATA_DIR_UNAVAILABLE` | mkdir, chmod, or provisioning ownership failed. This is the usual result of `--user 4242:4242` on a standard volume owned by uid 1000, because chmod fails before the account home lookup. Keep `BB_DATA_VOLUME` consistent, create the service through Compose before provisioning, and provision at `/var/lib/budget-broker` as uid 1000 |
| `LOCK_HELD` | Another process holds the data lock or the same-key lock. Stop that process. Never delete files or switch volumes or `HOME` to get around the lock |
| `LOCK_UNAVAILABLE` | The lock path, mode, ownership, symlink status, or format is invalid, or the runtime uid has no OS passwd entry, so the account home lookup fails. For `docker run --user 4242:4242` to even reach that lookup, uid 4242 must own the volume and lock files, and the earlier RPC and custody checks must pass, including a master file owned by uid 4242. A standard volume owned by the image usually gives `DATA_DIR_UNAVAILABLE` first. Use the supported image uid 1000, which has a passwd entry and a home. Do not work around this with `HOME` or `TMPDIR`, and do not switch trust-root volumes. Check for a private 0700 directory and 0600 SQLite files owned by the uid. The daemon never repairs permissions |
| `RPC_UNAVAILABLE` | The RPC transport or HTTP failed at startup. Restore the testnet RPC service. Never bypass the identity check |

If the RPC is reachable but reports a wrong chain identity or one the daemon cannot prove, or if the config names mainnet, the daemon reports `MAINNET_REFUSED` (exit 1) instead of `RPC_UNAVAILABLE`, and custody stays locked. `BB_IMAGE` selects the image and `BB_DATA_VOLUME` is the only private trust-root volume. Separate containers, hosts, or OS users do not share locks. Never fix a held lock by switching to a fresh volume.

A minimal bug report has the Node and package versions, the stable code or reason, the request ID and state, and the public transaction hash if there is one. Do not attach `.env`, token files, encrypted or unlocked key material, config files with secrets, the raw database, the process environment, or full RPC or SDK errors. Freeze if you suspect misuse. Keep backups and checkpoints protected and out of agents' reach.
